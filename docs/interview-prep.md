## Предметная область: спотовая торговля vs бинарные опционы

**Важно:** TradeSim — это **спотовая биржевая торговля** (Spot Trading), а не бинарные опционы.

**Спотовая торговля (наша система):**
- Пользователь владеет активом (акции, криптовалюта)
- Лимитные ордера попадают в стакан (Order Book)
- Матчинг-движок сопоставляет заявки (Price-Time Priority)
- Рыночные ордера исполняются мгновенно
- Есть портфель: купил 10 AAPL — они в портфеле
- Backend сложный: ACID, конкурентный доступ, real-time стриминг

**Бинарные опционы (не наша система):**
- "Ставка" на направление цены (вверх/вниз) через фиксированное время
- Нет стакана, нет матчинга, нет владения активом
- Backend тривиальный: принять ставку, подождать, выдать результат
- Пример: WR Trading Simulator

**На собеседовании:**
- «Чем ваша система отличается от бинарных опционов?»
- Ответ: "В спотовой торговле есть реальный стакан заявок, матчинг-движок, владение активом. Это распределенная система с ACID-транзакциями, конкурентным доступом и real-time стримингом. Бинарные опционы — просто ставка на направление."

## Архитектура и дизайн систем

### Вопросы

**«Спроектируйте биржевую торговую систему»**

**Что спрашивают:**
- Какие сервисы выделите?
- Как обеспечить консистентность?
- Как масштабировать матчинг?
- Какие базы данных выберете?

**Ответ (на основе TradeSim):**
1. **Сервисы:** Account (пользователи), Order (ордера), Matching Engine (стакан), Market Data (котировки), Analytics (история), Payment (платежи), Notification (уведомления).
2. **Консистентность:** ACID в PostgreSQL для ордеров и баланса. Outbox Pattern для отправки событий в Kafka. Saga для компенсации ошибок.
3. **Масштабирование матчинга:** шардирование по `asset_id` (консистентное хеширование). Каждый шард — отдельный инстанс.
4. **Базы:** PostgreSQL (транзакции), Redis (кеш, стакан в памяти), Kafka (события), MongoDB (логи).

**«Монолит или микросервисы?»**

- **Монолит:** команда < 5, нет четких доменных границ, не нужно масштабировать отдельные части.
- **Микросервисы:** большая команда, разные циклы деплоя, независимое масштабирование (матчинг отдельно от аналитики).
- **TradeSim:** микросервисы для изучения, но в MVP — монолит.

**«Как обеспечить надежность доставки событий?»**

- **Outbox Pattern:** пишем событие в таблицу `outbox` в той же транзакции, что и бизнес-данные. Отдельный воркер читает и отправляет в Kafka.
- **Почему не 2PC:** медленно, сложно, не все БД поддерживают.
- **At-least-once delivery:** Kafka гарантирует доставку, consumer должен быть идемпотентным.

## Базы данных

### PostgreSQL

**«Какие индексы нужны для таблицы orders?»**

```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);
CREATE INDEX idx_orders_status ON orders(status);
CREATE INDEX idx_orders_user_status ON orders(user_id, status);  -- Composite
CREATE INDEX idx_orders_created_at ON orders(created_at DESC);
```

**«Чем B-tree отличается от Hash индекса?»**
- B-tree: сортировка, диапазоны, равенство. Универсальный.
- Hash: только равенство. Быстрее для точного поиска, но не поддерживает ORDER BY, диапазоны.

**«Что такое MVCC?»**
- Multi-Version Concurrency Control.
- Каждая транзакция видит снимок данных на момент начала.
- Чтение не блокирует запись (и наоборот).
- Приводит к bloat (мусорным версиям строк) — нужен VACUUM.

**«Как работает SERIALIZABLE isolation level?»**
- Самый строгий уровень. Гарантирует, что результат параллельных транзакций эквивалентен их последовательному выполнению.
- Реализован через predicate locking в PostgreSQL.
- Trade-off: больше блокировок, медленнее.

### Redis

**«Чем Redis отличается от PostgreSQL?»**

| | Redis | PostgreSQL |
|---|---|---|
| Хранение | In-memory (опционально persistence) | Disk-based |
| Скорость | Микросекунды | Миллисекунды |
| Структуры | Strings, Lists, Sets, Hashes, Sorted Sets, Streams | Таблицы, JSONB |
| Транзакции | Нет ACID (Redis 6.2+ — limited) | Полный ACID |
| Масштабирование | Cluster (шардирование) | Replication, partitioning |

**«Когда использовать Redis Pub/Sub, а когда Streams?»**
- **Pub/Sub:** real-time уведомления, чат. Не хранит сообщения (если consumer offline — пропускает).
- **Streams:** очереди задач, event sourcing. Хранит сообщения, поддерживает consumer groups.

**«Почему Sorted Set (ZSET) для стакана?»**
- O(log N) на вставку/удаление.
- Автоматическая сортировка по score (цена).
- Для bid: score = -price (сортировка по убыванию).
- Для ask: score = price (сортировка по возрастанию).

## Асинхронность

### Asyncio

**«Как работает asyncio.Lock?»**
- Не блокирует поток (thread), а приостанавливает корутину.
- Когда lock свободен — следующая корутина в очереди продолжается.
- Важно: `async with lock`, не `await lock.acquire()` (можно забыть release).

**«Чем asyncio.Lock отличается от threading.Lock?»**
- threading.Lock: блокирует поток ОС (GIL в Python). Дорого.
- asyncio.Lock: кооперативная многозадачность, один поток, переключение корутин.

**«Что такое event loop?»**
- Цикл, который управляет выполнением корутин.
- Собирает готовые к выполнению задачи (I/O completed, timeout, etc).
- В Python — `asyncio.get_event_loop()` или `asyncio.run()`.

**«Когда использовать threading, multiprocessing, asyncio?»**
- **Asyncio:** много I/O (сетевые запросы, WebSocket). Один поток, кооперативная многозадачность.
- **Threading:** I/O + немного CPU. GIL ограничивает параллелизм CPU-bound задач.
- **Multiprocessing:** CPU-bound (математика, обработка данных). Обходит GIL.

## Аутентификация

### JWT vs Sessions

**«Чем JWT отличается от сессий?»**

| | JWT | Sessions |
|---|---|---|
| State | Stateless (токен содержит данные) | Stateful (хранятся на сервере) |
| Масштабирование | Легко (проверка подписи) | Требует shared storage (Redis) |
| Отзыв | Сложно (blacklist, короткий TTL) | Легко (удалить из Redis) |
| Размер | Большой (base64 заголовок + payload) | Маленький (session ID) |
| CSRF | Не подвержен | Требует защиты (token) |
| Use case | API, микросервисы, мобильные | Веб-приложения, админки |

**«Почему RS256, а не HS256?»**
- HS256: симметричный (один ключ). Если скомпрометирован — все сломано. Ключ нужно раздавать всем сервисам.
- RS256: асимметричный (приватный + публичный). Публичный ключ можно безопасно раздать. Приватный — только на auth сервисе.

**«Как отозвать JWT токен?»**
- Короткий TTL access token (5-15 минут).
- Refresh token в httpOnly cookie.
- Blacklist (Redis) для срочного отзыва.
- Или: хранить все active sessions в Redis, проверять при каждом запросе (теряем statelessness).

**«Что такое refresh token?»**
- Долгоживущий токен (7-30 дней) для получения новой пары access + refresh.
- Хранится в httpOnly cookie (защита от XSS).
- При компрометации — можно отозвать (храним в БД/Redis).

## Микросервисы

### Взаимодействие

**«REST vs gRPC vs GraphQL»**

| | REST | gRPC | GraphQL |
|---|---|---|---|
| Протокол | HTTP/1.1 | HTTP/2 | HTTP/1.1 или HTTP/2 |
| Формат | JSON | Protobuf (бинарный) | JSON |
| Schema | Нет (OpenAPI) | Строгая (.proto) | Строгая (SDL) |
| Streaming | Нет | Да (server, client, bidirectional) | Подписки (WebSocket) |
| Кэширование | HTTP caching | Сложно | Сложно |
| Use case | Публичные API | Сервис-сервис | Гибкие клиентские запросы |

**«Почему Kafka, а не RabbitMQ?»**

| | Kafka | RabbitMQ |
|---|---|---|
| Модель | Log-based (append-only) | Queue-based |
| Throughput | 100k+ msg/s | 20k+ msg/s |
| Persistence | Да (retention) | Опционально |
| Replay | Да (перечитать с offset) | Нет (потреблено — удалено) |
| Routing | Топик + partition | Exchange + routing key |
| Use case | Event sourcing, логи | Task queues, RPC |

**«Что такое Eventual Consistency?»**
- Гарантия, что если данные не изменяются, все реплики со временем сойдутся.
- В микросервисах: Order Service создал ордер, но Analytics еще не увидел (задержка Kafka).
- Trade-off: доступность vs консистентность (CAP теорема).

**«Как работает Circuit Breaker?»**
- Состояния: Closed (норма) → Open (много ошибок) → Half-Open (пробуем восстановиться).
- При Open: быстрый отказ (fallback), не ждем таймаута.
- Защита от каскадных отказов.

## DevOps и инфраструктура

### Docker

**«Чем Docker отличается от VM?»**
- Docker: шарит ядро ОС (host), изолирует процессы (cgroups, namespaces).
- VM: полная изоляция (hypervisor), свое ядро, больше ресурсов.
- Docker легче (MB vs GB), быстрее запускается.

**«Что такое multi-stage build?»**
- Несколько FROM в Dockerfile.
- Stage 1 (builder): устанавливаем зависимости, компилируем.
- Stage 2 (runtime): копируем только артефакты, легкий образ (alpine/slim).
- Результат: меньше размер, меньше attack surface.

### CI/CD

**«Что такое blue-green deployment?»**
- Две идентичные среды: blue (текущая), green (новая).
- Роутер переключает трафик с blue на green.
- При ошибке — мгновенный rollback (переключение обратно).
- Zero downtime.

**«Чем trunk-based development отличается от Git Flow?»**
- **Trunk-based:** все в main, feature flags, короткие ветки (1-2 дня).
- **Git Flow:** main + develop + feature + release + hotfix. Сложнее, дольше циклы.
- Современный подход — trunk-based (быстрее, проще).

### Мониторинг

**«Что такое RED метод?»**
- **Rate:** количество запросов в секунду.
- **Errors:** процент ошибок.
- **Duration:** время обработки (latency).
- Применяется к каждому сервису.

**«Чем histogram отличается от summary в Prometheus?»**
- **Histogram:** агрегируется (суммируется across instances). Квантили считаются на стороне сервера.
- **Summary:** не агрегируется. Квантили считаются на стороне клиента (точнее, но нельзя сложить).
- Для распределенных систем — histogram.

**«Что такое p50, p95, p99?»**
- **p50 (median):** 50% запросов быстрее этого значения.
- **p95:** 95% запросов быстрее. Показывает «хвост» распределения.
- **p99:** 99% запросов быстрее. Важно для SLA.
- Пример: p50 = 10ms, p95 = 100ms, p99 = 500ms → проблема с «хвостом».

## Алгоритмы и структуры данных

### Стакан заявок (Order Book)

**«Как хранить стакан?»**

**Вариант 1: Sorted Dictionary (TreeMap)**
- Bid: ключ = цена, значение = список ордеров. Сортировка по убыванию.
- Ask: ключ = цена, значение = список ордеров. Сортировка по возрастанию.
- Вставка/удаление: O(log N).
- Лучшая цена: O(1) (первый элемент).

**Вариант 2: Redis Sorted Set (ZSET)**
- Bid: `ZADD bids:{asset_id} {-price} order_id`.
- Ask: `ZADD asks:{asset_id} {price} order_id`.
- O(log N) на вставку. `ZRANGE`/`ZREVRANGE` для получения лучших цен.

**Вариант 3: Heap (Priority Queue)**
- Min-heap для ask, max-heap для bid.
- O(log N) вставка, O(1) лучшая цена.
- Но: удаление произвольного ордера — O(N).

**TradeSim:** в MVP — Sorted Dictionary (Python dict + sorted). В production — Redis ZSET или специализированная структура.

### Матчинг (Matching)

**«Алгоритм Price-Time Priority»**
1. Сортируем bid по убыванию цены, затем по времени.
2. Сортируем ask по возрастанию цены, затем по времени.
3. Берем лучший bid и лучший ask.
4. Если bid.price >= ask.price — совершаем сделку.
5. Повторяем, пока bid.price < ask.price.

**Сложность:**
- Вставка ордера: O(log N) (вставка в sorted structure).
- Матчинг: O(M * log N), где M — количество исполненных сделок.

## Python специфика

**«Что такое GIL?»**
- Global Interpreter Lock.
- Блокирует выполнение байткода Python в одном потоке.
- Значит: threading не ускоряет CPU-bound задачи (один поток выполняет Python код).
- Но: threading ускоряет I/O-bound (пока один поток ждет I/O, другой может работать).
- Обход: multiprocessing (отдельные процессы), asyncio (кооперативная многозадачность), C extensions (release GIL).

**«Чем list отличается от tuple?»**
- list: mutable, динамический массив, O(1) append (amortized), O(N) insert/delete в середину.
- tuple: immutable, хешируемый (можно использовать как ключ dict), быстрее создание.

**«Что такое @property?»**
- Дескриптор, позволяет обращаться к методу как к атрибуту.
- Полезно для валидации, lazy loading, кеширования.

**«Как работает asyncio.gather?»**
- Запускает несколько корутин параллельно.
- Возвращает результаты в том же порядке (не по завершению).
- Если `return_exceptions=True` — не бросает исключение, а возвращает его как результат.
