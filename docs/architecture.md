# Архитектура TradeSim

## Почему микросервисы?

**Контекст:** проект учебный, цель — изучить технологии.

**Обоснование:**
- Каждый сервис использует разный фреймворк (Django, FastAPI, aiohttp) для изучения
- Независимое масштабирование (Matching Engine можно масштабировать отдельно)
- Изоляция отказов (падение Notification Worker не останавливает торги)
- Отдельные циклы деплоя

**Альтернатива:** Монолит (Django + DRF). Проще, но не дает изучить межсервисное взаимодействие, gRPC, event-driven архитектуру. Для собеседования важно понимать и то, и другое.

**Когда монолит лучше:**
- Команда < 5 человек
- Нет четких доменных границ
- Не нужно масштабировать отдельные части

## Потоки данных

### 1. Размещение ордера

```
Клиент → API Gateway → Order Service → [валидация JWT]
                                    → [проверка баланса через Account Service]
                                    → [списание через Payment Service]
                                    → [Outbox: запись в БД]
                                    → [gRPC → Matching Engine]
                                    → [Kafka: OrderPlaced]
```

**Почему так:**
- JWT проверяем на Gateway (единая точка входа)
- Баланс проверяем синхронно (нельзя продать то, чего нет)
- Payment — асинхронно через Celery (не блокируем торги)
- Outbox гарантирует доставку в Matching Engine

### 2. Исполнение сделки

```
Matching Engine → [Kafka: TradeExecuted]
                → History Service (сохранение)
                → Notification Worker (email)
                → Order Service (обновление статуса)
```

**Почему Kafka:**
- Надежная доставка (at-least-once)
- Множество потребителей (history, notification, analytics)
- Сохранение истории (retention)

### 3. Котировки

```
Binance WS → Market Data Service → [Redis: последняя цена]
                                 → [Kafka: тики]
                                 → [WS → клиенты]
```

**Почему Redis + Kafka:**
- Redis — быстрый доступ к текущей цене (O(1))
- Kafka — история для графиков и аналитики

## Границы сервисов (Bounded Contexts)

| Сервис | Ответственность | Почему отдельно |
|--------|----------------|-----------------|
| **Account** | Пользователи, аутентификация, баланс | Единая точка правды о пользователях. JWT выдает здесь. |
| **Order** | Жизненный цикл ордера, валидация | Сложная бизнес-логика (лимитные/рыночные, частичное исполнение). |
| **Matching Engine** | Стакан, матчинг | Требует минимальной задержки, хранит состояние в памяти. |
| **Market Data** | Внешние котировки, кеширование | Интеграция с внешними API, отдельный протокол (WebSocket). |
| **Analytics** | История, графики, отчеты | Тяжелые запросы, отдельная БД, не влияет на торги. |
| **Payment** | Пополнение/вывод средств | Интеграция с внешними платежными системами (в будущем). |
| **Notification** | Email, push | Не критично, может отставать. |

## Паттерны

### API Gateway
- Единая точка входа для клиентов
- Rate limiting, JWT verification, routing
- **Альтернатива:** Клиент ходит напрямую в сервисы (сложнее управлять)

### Outbox Pattern
- Запись события в таблицу `outbox` в той же транзакции, что и ордер
- Отдельный воркер читает и отправляет в Kafka
- **Зачем:** гарантия at-least-once delivery без 2PC

### Saga Pattern
- Если списание денег прошло, но матчинг упал — компенсирующая транзакция (возврат денег)
- **В MVP:** упрощенная версия через Celery retry + dead letter queue

### CQRS (упрощенный)
- Order Service отвечает за запись (торговля)
- Analytics Service отвечает за чтение (графики, история)
- Разные модели данных для разных задач

### Circuit Breaker
- Если Matching Engine недоступен — быстрый отказ (503) вместо таймаута
- Защита от каскадных отказов

## Масштабирование

### Matching Engine
- **Проблема:** один инстанс = bottleneck
- **Решение:** шардирование по `asset_id` (AAPL на инстанс 1, BTC на инстанс 2)
- **Как:** консистентное хеширование `asset_id % N`

### Order Service
- **Масштабирование:** горизонтальное (N инстансов за Nginx)
- **Состояние:** stateless (все в БД)

### Account Service
- **Масштабирование:** горизонтальное, но JWT verification на Gateway снижает нагрузку
