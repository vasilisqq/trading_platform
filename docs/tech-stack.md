# Обоснование технологического стека

Каждая технология выбрана не случайно. Ниже — обоснование с альтернативами и контекстом выбора.

---

## Язык: Python 3.12+

**Почему:**
- Основной язык для backend в целевых компаниях (Яндекс, Тинькофф, Авито)
- Богатая экосистема для веба, данных, инфраструктуры
- Асинхронность (asyncio) встроена в язык

**Альтернативы:**
- **Go** — лучше для высоконагруженных систем (матчинг), но сложнее для изучения многих концепций (ORM, DI)
- **Java/Kotlin** — много boilerplate, медленнее разработка
- **Node.js** — callback hell, слабая типизация

**Для собеседования:**
- «Почему Python, а не Go?» — Python быстрее разрабатывать, богатая экосистема. Go выбрал бы для чистого матчинга с миллионами RPS.

## Веб-фреймворки

### Django + DRF (Account Service)

**Почему:**
- Встроенная админка (управление пользователями)
- ORM с миграциями из коробки
- Аутентификация (sessions, JWT) готова
- Зрелая экосистема

**Альтернативы:**
- **FastAPI** — можно, но придется писать админку и миграции самому
- **Flask** — слишком минималистичный для сервиса с пользователями

**Когда НЕ Django:**
- Высоконагруженные API (много JSON, мало бизнес-логики)
- Микросервис с 2 эндпоинтами (перегруз)

### FastAPI (Order, Analytics Services)

**Почему:**
- Native async/await (высокая производительность на I/O)
- Автоматическая валидация через Pydantic
- Автоматическая документация (OpenAPI/Swagger)
- Dependency Injection из коробки

**Альтернативы:**
- **Django Ninja** — быстрее, если уже знаете Django
- **aiohttp** — ниже уровень, больше boilerplate
- **Tornado** — устаревает, меньше community

**Для собеседования:**
- «Почему FastAPI, а не Django?» — FastAPI лучше для API-first сервисов с высоким RPS. Django — для CRUD с админкой.

### aiohttp (Market Data Service)

**Почему:**
- Низкоуровневый контроль над WebSocket соединениями
- Легкий фреймворк для сервиса с 1 задачей (проксирование котировок)
- Показывает разницу между «высокоуровневым» (FastAPI) и «низкоуровневым» подходами

**Альтернативы:**
- **FastAPI** — тоже поддерживает WebSocket, но aiohttp дает больше контроля
- **websockets** library — еще ниже уровень, почти чистый Python

## Базы данных

### PostgreSQL

**Почему:**
- ACID транзакции (критично для финансовых операций)
- Сложные запросы, JOIN, CTE
- JSONB для полуструктурированных данных
- Репликация из коробки

**Альтернативы:**
- **MySQL** — тоже ACID, но PostgreSQL лучше с JSON, оконными функциями
- **SQLite** — только для тестов
- **MongoDB** — не подходит для транзакционных операций (в начале)

**Для собеседования:**
- «Почему PostgreSQL?» — ACID, сложные запросы, JSONB. Для финансов — только реляционная БД.

### Redis

**Почему:**
- In-memory (микросекундная задержка)
- Pub/Sub для real-time
- Sorted Sets (ZSET) — идеально для стакана заявок (сортировка по цене)
- Кеширование сессий, rate limiting

**Альтернативы:**
- **Memcached** — проще, но нет Pub/Sub, структур данных
- **KeyDB** — форк Redis, быстрее, но меньше community

**Для собеседования:**
- «Чем Redis отличается от PostgreSQL?» — Redis in-memory, скорость, структуры данных. PostgreSQL — персистентность, ACID.

### MongoDB (опционально)

**Почему:**
- Логи, аналитика, история котировок (полуструктурированные данные)
- Горизонтальное масштабирование (sharding)

**Альтернативы:**
- **ClickHouse** — лучше для аналитики, но сложнее
- **PostgreSQL JSONB** — проще, но медленнее на больших объемах

## gRPC + Protobuf

**Почему:**
- Бинарный протокол (меньше трафика, быстрее сериализация)
- HTTP/2 (мультиплексирование, server push)
- Строгая типизация через .proto (контракты)
- Streaming (server-side, client-side, bidirectional)

**Где используем:**
- Order Service → Matching Engine (высокая частота, низкая задержка)

**Альтернативы:**
- **REST + JSON** — проще отлаживать (curl), но медленнее, больше трафика
- **GraphQL** — не подходит для сервис-сервис взаимодействия (слишком гибкий)
- **WebSocket** — можно, но нет строгих контрактов

**Для собеседования:**
- «Почему gRPC?» — бинарный, HTTP/2, streaming, строгие контракты. Для внутреннего взаимодействия.
- «Когда REST лучше?» — публичные API, отладка, кэширование (HTTP caching).

## Kafka / Redis Streams

### Apache Kafka

**Почему:**
- Высокая пропускная способность (100k+ сообщений/сек)
- Persistence (сообщения хранятся, можно перечитать)
- Consumer Groups (масштабирование потребителей)
- Retention policy (хранение истории)

**Где используем:**
- TradeExecuted events (история, аналитика, уведомления)
- Market Data ticks (котировки)

**Альтернативы:**
- **RabbitMQ** — лучше для сложной маршрутизации (routing keys), но меньше throughput
- **Redis Streams** — проще, но меньше durability, нет consumer groups как в Kafka
- **NATS** — легкий, но меньше экосистема

### Redis Streams (для MVP)

**Почему:**
- Проще настроить (один Redis контейнер)
- Достаточно для учебного проекта
- Можно перейти на Kafka без изменения кода (абстракция)

**Для собеседования:**
- «Почему Kafka, а не RabbitMQ?» — throughput, persistence, replay. RabbitMQ — для сложной маршрутизации.
- «Чем Redis Streams отличается от Pub/Sub?» — Streams хранят сообщения, Pub/Sub — нет.

## Celery + RabbitMQ/Redis

**Почему:**
- Асинхронные задачи (email, отчеты, платежи)
- Retry с exponential backoff
- Dead Letter Queue (DLQ) для ошибок
- Распределенное выполнение (много воркеров)

**Где используем:**
- Notification Worker (email при исполнении ордера)
- Payment Service (асинхронные платежи)
- Генерация отчетов

**Альтернативы:**
- **Rq** — проще, но меньше функционала (нет retry из коробки)
- **Dramatiq** — быстрее Celery, но меньше community
- **Asyncio background tasks** — только в рамках одного процесса

**Для собеседования:**
- «Почему Celery?» — зрелый, retry, DLQ, мониторинг (Flower). Для production задач.
- «Когда asyncio tasks лучше?» — быстрые фоновые задачи в рамках одного процесса (например, кеширование).

## WebSockets

**Почему:**
- Full-duplex (двусторонняя связь)
- Низкая задержка для real-time
- Подходит для стриминга котировок и обновлений портфеля

**Альтернативы:**
- **SSE (Server-Sent Events)** — проще (HTTP), но только server→client
- **Long Polling** — устарел, высокая нагрузка на сервер
- **WebRTC** — для P2P, избыточен

**Для собеседования:**
- «WebSocket vs SSE?» — WebSocket двусторонний, SSE проще. Для котировок — WebSocket (нужны heartbeat, управление подписками).

---

## GraphQL (Strawberry)

**Почему:**
- Клиент запрашивает только нужные поля (меньше трафика)
- Одна точка входа для всех запросов
- Типизация схемы (автодокументация)
- Подписки (real-time через WebSocket)

**Где используем:**
- Analytics Service (гибкие запросы истории, графиков)

**Альтернативы:**
- **REST** — проще, но over-fetching/under-fetching
- **gRPC** — для сервис-сервис, не для клиентов

**Для собеседования:**
- «Почему GraphQL?» — гибкость запросов, типизация. Минусы — N+1 problem, сложность кэширования.

---

## Docker + Docker Compose

**Почему:**
- Изоляция зависимостей
- Единообразие окружений (dev = prod)
- Легкий запуск всей инфраструктуры одной командой

**Альтернативы:**
- **Vagrant** — тяжелее (VM вместо контейнеров)
- **Nix** — сложнее в изучении
- **System packages** — конфликты версий

**Для собеседования:**
- «Чем Docker отличается от VM?» — Docker шарит ядро ОС, VM — нет. Docker легче и быстрее.

---

## CI/CD: GitHub Actions

**Почему:**
- Встроен в GitHub (без дополнительных сервисов)
- Большая библиотека actions
- Бесплатно для open-source

**Что автоматизируем:**
- Линтеры (ruff, mypy)
- Тесты (pytest)
- Сборка Docker образов
- Security scan (Trivy)

**Альтернативы:**
- **GitLab CI** — похож, но требует GitLab
- **Jenkins** — гибче, но сложнее в поддержке
- **CircleCI** — платный для приватных репозиториев

## Мониторинг: Prometheus + Grafana

**Почему:**
- Pull модель (сервер опрашивает метрики) — надежнее
- Мощный язык запросов (PromQL)
- Grafana — лучшие дашборды
- Экосистема Alertmanager

**Метрики:**
- Counter: количество ордеров, сделок
- Histogram: latency матчинга (p50, p95, p99)
- Gauge: размер стакана, количество подключений

**Альтернативы:**
- **InfluxDB** — push модель, лучше для IoT
- **Datadog** — платный, но больше функций из коробки
- **Zabbix** — устаревает

**Для собеседования:**
- «Что мониторите?» — RED метод (Rate, Errors, Duration) + бизнес-метрики.
- «Чем histogram отличается от summary?» — histogram агрегируется, summary — нет.

---

## Логирование: Structlog + Loki

**Почему:**
- JSON-логи (структурированные, парсятся автоматически)
- Contextual logging (request_id, user_id в каждой строке)
- Loki — легковесная альтернатива ELK

**Альтернативы:**
- **ELK (Elasticsearch + Logstash + Kibana)** — тяжелее, но мощнее
- **Splunk** — платный
- **Plain text logs** — сложно парсить, не масштабируется

**Для собеседования:**
- «Зачем JSON-логи?» — структура, поиск, агрегация. Plain text — для локальной разработки.

---

## Трейсинг: OpenTelemetry + Jaeger

**Почему:**
- Стандарт (не привязан к вендору)
- Автоинструментация (минимум кода)
- Визуализация пути запроса через микросервисы

**Альтернативы:**
- **Zipkin** — проще, но меньше функций
- **AWS X-Ray / Google Cloud Trace** — vendor lock-in

**Для собеседования:**
- «Зачем трейсинг?» — найти bottleneck в распределенной системе. Метрики показывают «что», трейсы — «где».

---

## Тестирование: Pytest + Testcontainers

**Почему:**
- Pytest — стандарт для Python, богатая экосистема плагинов
- Testcontainers — интеграционные тесты с реальными БД и Kafka
- Locust — нагрузочное тестирование на Python

**Альтернативы:**
- **Unittest** — встроен, но меньше функций
- **Robot Framework** — для e2e, сложнее
- **JMeter** — для нагрузки, но не Python
