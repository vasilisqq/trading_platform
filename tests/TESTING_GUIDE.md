## 1. Методология

### 1.1 Пирамида тестов

Тестов должно быть **тем больше, чем ниже уровень** — нижние быстрые и дешёвые:

```
        /\        API / e2e  — МАЛО. Через client. Проверяют то, что живёт
       /  \                    только на HTTP-уровне: статус-код, форму JSON,
      /----\                   куки, что роут вообще вызывает сервис.
     /      \     Integration — СРЕДНЕ. Репозитории и get_current_user
    /--------\                  против реальной тестовой БД (db_session).
   /          \   Unit         — МНОГО. Чистая логика без БД/сети: security.py,
  /____________\                 валидаторы схем, ветвление сервисов (repo замокан).
```

Антипаттерн — «рожок мороженого»: когда всё тестируется через медленные e2e. Твой `test_google_callback` — как раз туда.

### 1.2 «Нужен ли тест на каждый эндпоинт?» — короткий ответ

**И да, и нет:**
- **Да** — у каждого эндпоинта пусть будет 1 API-тест: успешный путь + одна ключевая ошибка (401/403/422). Он проверяет проводку: маршрут подключён, схема валидирует вход, статус и куки верные.
- **Нет** — не прогоняй *каждую ветку логики* через HTTP. Если у `UserService.login` 5 веток (нет юзера / неверный пароль / заблокирован / email не подтверждён / успех) — эти 5 веток тестируются **юнит-тестом сервиса** с замоканным репозиторием. На уровне API хватит 1–2 (успех + один отказ).

> Правило: **логику тестируем на самом низком слое, где она живёт.** Верхние слои проверяют только то, что добавляют сами. Так тесты не дублируются и не тормозят.

### 1.3 Принципы хорошего теста

1. **AAA** — три части в каждом тесте:
   ```
   # Arrange — подготовили данные/моки
   # Act     — вызвали то, что тестируем (одно действие)
   # Assert  — проверили результат
   ```
2. **Одна проверка поведения на тест.** Не «проверю логин и заодно рефреш».
3. **Осмысленные assert'ы.** Не `assert x is not None`, а `assert user.email == "a@b.c"`. Проверяй именно то поведение, ради которого пишешь тест.
4. **Поведение, а не реализацию.** Чем меньше моков внутренностей — тем ценнее тест. Мокай только внешние границы (БД там, где не нужна; Redis; HTTP к Google; отправку письма).
5. **Негативные пути обязательны.** Ошибки и валидация ломаются чаще happy-path. На каждый «успех» держи в уме «а что если нет».
6. **Детерминизм.** Никаких `sleep` и зависимости от текущего времени. Срок JWT проверяй, подделав `exp` в прошлом (см. 3.1), а не ожиданием.
7. **Изоляция.** Тесты не зависят друг от друга и от порядка. У тебя это уже даёт `db_session` (откат транзакции).
8. **Имя = что проверяем.** `test_login_disabled_user_raises_disabled_error`, а не `test_login_2`.

### 3.1 Unit — новый файл `tests/test_security.py`
Тестируем `src/core/security.py`. Чистые функции, БД не нужна — самые быстрые и ценные тесты.

- [X] `hash_password` + `verify_password`: правильный пароль → `True`, неправильный → `False`.
- [X] Пароль **длиннее 72 байт** всё равно верифицируется (проверяем, что sha256-пре-хэш обходит лимит bcrypt). *Подсказка: сгенерируй строку из 100+ символов.*
- [X] `create_access_token` → `decode_access_token`: в payload есть `sub`, `type == "access"`, `jti`, `exp`, `iat`.
- [X] `create_refresh_token` → `decode_refresh_token`: `type == "refresh"`, `jti` нет.
- [X] **Перекрёстный тип**: access-токен в `decode_refresh_token` → `jwt.InvalidTokenError`, и наоборот.
- [ ] Неизвестный тип в `_create_token` → `ValueError`.
- [ ] *(опционально)* `verify_exp=False`: истёкший токен всё равно отдаёт payload. Это твоё дизайн-решение — на нём держится `logout` (достаёт `jti` из уже истёкшего токена), поэтому проверить можно. *Подсказка: собери токен с `exp` в прошлом через `jwt.encode({..., "exp": <в прошлом>, "type": "access"}, settings.SECRET_KEY.get_secret_value(), "HS256")` — ключ тот же, что в приложении, иначе упадёшь на подписи, а не на сроке.*

> ⚠️ **Тест «истёкший → `ExpiredSignatureError`» здесь НЕ пишем.** Само исключение при протухшем `exp` кидает PyJWT, а `decode_access_token` его не ловит и не меняет — это поведение библиотеки, не твоё. Твою *реакцию* на истечение (маппинг в 401 "Token expired") даёт `get_current_user` в `src/core/dependencies.py`, и тестируется она на уровне эндпоинта `GET /me` (см. 3.5). Правило: на стыке с библиотекой тестируй **свою реакцию** на её результат, а не факт, что библиотека работает.

## 4. Известные баги — покрыть тестом «правильного» поведения и пометить

Пиши тест на то, как **должно** быть. Если из-за бага тест не проходит — не удаляй его, а помечай:
```
@pytest.mark.xfail(reason="bug: session.delete не await, сессия не удаляется", strict=True)
```
`strict=True` заставит CI ругаться, если баг вдруг починят (тест станет `XPASS`) — тогда снимешь метку.

1. **`SessionRepository.delete` без `await`** — `src/repositories/session_repository.py:34`, вызывается в `UserService.refresh` (`src/services/user_service.py:77`). В async SQLAlchemy `AsyncSession.delete()` — корутина; без `await` удаление не выполняется → при ротации старый refresh-токен остаётся живым. Тест «после refresh старый токен не работает» → `xfail`.
2. **Слепой `update_password`** — `src/repositories/user_repository.py:50`. `UPDATE` без проверки rowcount: `reset_password` «успешен» даже для несуществующего email, лишь бы токен был валиден. Тест-документация этого → `xfail`/`TODO`.
3. **Забытые `print()`** в `logout` — `src/api/auth.py:81,86`. Не тестируется, просто в список на удаление.
4. **`UserService.register`** аннотирован `-> None`, но возвращает `user` (`src/services/user_service.py:29`) — мелочь, заметка.
5. Наблюдения (не баги, но обсудить): `resend-verification` принимает `email` query-параметром, а не телом; CORS `allow_origins=["*"]` + `allow_credentials=True` — невалидная комбинация; `Session.expires_at` при refresh не проверяется (только факт наличия сессии).

> Эти пункты складывай в раздел «Известные проблемы» здесь же или в отдельный `tests/KNOWN_ISSUES.md`.

```bash

# с покрытием — видно, какие строки src/ ещё не покрыты
```
